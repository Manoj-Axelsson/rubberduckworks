

"Leave the pond cleaner than you found it."

The Pond Manager's Rule

---

This repository is not a code repository. It is an Engineering Systems Laboratory.

That means the governance should explain how the laboratory operates, not just who can merge a PR. RubberDuckWorks is maintained by many contributors, but every contributor serves as the Pond Manager for the duration of their commit. Their responsibility is not ownership—it is stewardship.

--- 

1. Purpose 

RubberDuckWorks exists as an Engineering Systems Laboratory dedicated to learning in public through software engineering, systems thinking, documentation, and continuous improvement. The repository values understanding over complexity and stewardship over ownership.

---

2. The Laboratory Model 
   
- This repository is treated as a laboratory.
- Experiments are encouraged.
- Documentation is considered a first-class artifact.
- Failures are documented rather than hidden.
- Every change should teach something to the next visitor.

---

3. The Pond Manager Principle

Every contributor becomes the Pond Manager for the duration of their commit.

The Pond Manager owns nothing permanently.

Instead, the Pond Manager accepts temporary responsibility for improving the pond before leaving it for the next visitor.

The Pond Manager:
- removes obsolete files
- improves documentation
- simplifies complexity
- questions unnecessary dependencies
- leaves meaningful commit history.

The objective is simple: **Leave the pond cleaner than you found it.**

---

4. Engineering Principles

- Documentation is part of the product.
- Software should be understandable before it is clever.
- Every file must justify its existence.
- Repository history should tell a story.
- Small improvements compound over time.

---

5. Decision-Making

When multiple solutions exist, preference is given to the one that:
- reduces cognitive load
- improves maintainability
- supports collaboration
- remains understandable six months later.

---

6. Documentation First

Documentation is created alongside implementation.
- README files explain purpose.
- Governance explains behavior.
- Manifestos explain culture.
- Commits explain intent.
- Issues explain motivation.
- Pull Requests explain evolution.

---

7. Continuous Improvement

Improvements may be:
- technical,
- architectural,
- documentation,
- process,
- repository hygiene.

No improvement is considered too small.

---

8. Repository Hygiene

There are no loitering ducks in this pond.
- Generated files are ignored.
- Unused assets are removed.
- Dead code is deleted.
- Dependencies must justify their existence.
- Repository structure should communicate intent.

---

9. Definition of Done

Work is considered complete when:
- documentation is updated,
- commit messages are meaningful,
- issues are referenced,
- pull requests tell a coherent story,
- the repository is cleaner than before.

---

10. Amendment Process

- Governance is intentionally lightweight.
- Any contributor may propose changes through an Issue and Pull Request.
- Governance evolves through continuous improvement rather than rigid process.
